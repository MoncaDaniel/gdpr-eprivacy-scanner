# Security architecture

The scanner drives a real Chromium against URLs chosen by anonymous users,
from inside a cloud project. This page is the threat model and the controls
that answer it. Decisions: [ADR-0005](../adr/0005-ssrf-defence-in-depth.md),
[ADR-0011](../adr/0011-egress-proxy.md), [ADR-0008](../adr/0008-stored-values-are-fingerprinted.md).

## Assets

| Asset | Why it matters |
|---|---|
| Cloud metadata server (`169.254.169.254`, `metadata.google.internal`) | Serves the service account's OAuth tokens |
| Loopback services on the scanner host | Debug ports, the Playwright driver, the local DB |
| Private network (VPC, Neon over private paths later) | Lateral movement |
| Stored evidence bundles | Contain URLs, cookie metadata, DOM snapshots of third-party sites |

## Threats and controls

### T1: SSRF through the browser

Attacker input: the submitted URL, plus everything the page then does
(redirects, sub-resources, iframes, `fetch`, WebSockets, WebRTC).

```
              user URL
                 │
   ┌─────────────▼──────────────┐
   │ L1 intake: normalise (WHATWG│   refuses 0xa9fea9fe, localhost, *.internal,
   │ IPv4 forms), resolve, check │   single-label hosts, non-80/443 ports
   └─────────────┬──────────────┘
                 │
   ┌─────────────▼──────────────┐      route() check: attribution only
   │ Chromium (per-session       │─────►(ties refusals to a request)
   │ context, proxy <-loopback>) │
   └─────────────┬──────────────┘
                 │ every connection, unresolved host name
   ┌─────────────▼──────────────┐
   │ L2 EgressProxy: guard check │   refused CONNECT → 403
   │ → connect to the vetted IP  │   refused HTTP → closed, no bytes
   │ L3 peer re-check after      │   violation → socket closed before relay
   │    connect                  │
   └─────────────┬──────────────┘
                 │
   ┌─────────────▼──────────────┐
   │ L4 VPC egress firewall      │   (Phase 4) deny RFC1918, link-local, ULA
   └────────────────────────────┘
```

Address policy (`intake/ssrf_guard.py: non_public_reason`): refuse loopback,
link-local (metadata), unspecified, multicast, private, reserved, and anything
`ipaddress` does not mark as global (CGNAT, benchmarking, documentation).
IPv4 embedded in IPv6 (`::ffff:a.b.c.d`, `64:ff9b::/96`, `2002::/16`) is
unwrapped first. If a DNS answer mixes public and private addresses, the
whole host is refused.

**Why the proxy and not request interception:** Playwright's `route` is not
called for redirect hops, and Chromium would resolve DNS itself after our
check. Details and the failing test that showed it: ADR-0011.

**WebRTC:** launched with `--force-webrtc-ip-handling-policy` and
`disable_non_proxied_udp`, so ICE cannot open UDP to local addresses.

**Test-only relaxations:** `allow_loopback` and `allowed_ports=None` exist so
hermetic fixture sites can run on `127.0.0.1:<random>`. Link-local and private
ranges stay refused even then. Both default to off, and the settings
description says never to enable them in production.

### T2: Hostile page content

- Sessions use fresh, isolated contexts. Downloads and service workers are
  disabled. Nothing persists between sessions or scans.
- The DOM is serialised as inert text artefacts and never re-rendered by us.
  The Phase 2 HTML report must escape all of it (Jinja2 autoescape).
- Artefact paths are generated by us. `LocalArtifactStore` refuses absolute
  paths and `..` anyway.
- Per-session limits cap memory and disk use: requests (3000), DOM bytes
  (5 MB), frames (50).

### T3: Leaking third-party data through our own evidence

Cookie and storage values are reduced to keyed fingerprints with a per-scan
key that is never stored (ADR-0008). An integration test asserts known fixture
values never appear in `evidence.json`.

### T4: Abuse of the service (Phase 4)

Per-IP rate limiting (IPs hashed, short retention), a per-domain result cache,
a Cloud Run max-instances cap and a scan timeout. Tracked as risks R12/R13 in
the design review.

## Residual risks

| Risk | Status |
|---|---|
| Chromium zero-day reachable via hostile page | Mitigated by Phase 4 sandboxing (non-root container, no SA credentials beyond need, L4 firewall). Not eliminable in-process |
| Egress proxy bug lets a connection through | Defence in depth: L4 firewall. Proxy has dedicated unit tests including a deliberately lying guard |
| Non-HTTP egress from Chromium (e.g. future protocols) | Proxy config covers HTTP(S)/WS. WebRTC constrained by flags. L4 firewall is the backstop |
